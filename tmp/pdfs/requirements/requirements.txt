1 Introducción
El presente documento describe el análisis, diseño y especificación delSistema de Ges-
tión Operativa de las Aulas de Software, una solución informática orientada a op-
timizar los procesos administrativos y operativos desarrollados por la dependencia encar-
gada de la administración de las Aulas de Software de la Facultad de Ingeniería de la
Universidad Distrital Francisco José de Caldas.
Actualmente, gran parte de la operación diaria se realiza mediante un conjunto de hojas
de cálculo de Microsoft Excel complementadas con registros físicos y tableros manua-
les, los cuales concentran información relacionada con horarios académicos, asistencia de
docentes, disponibilidad de aulas, préstamos de prácticas libres, préstamo de equipos au-
diovisuales, control del software instalado, observaciones operativas y asignación de tareas.
Aunque esta herramienta ha permitido organizar la información durante varios años,
el crecimiento de la operación ha incrementado la complejidad de su administración,
generando procesos manuales repetitivos, validaciones constantes y una alta dependencia
del conocimiento del personal para la toma de decisiones.
Como respuesta a esta necesidad, se plantea el desarrollo delSistema de Gestión Ope-
rativa de las Aulas de Software, cuyo propósito es centralizar la información, automa-
tizar procesos operativos y proporcionar mecanismos de apoyo para la toma de decisiones,
permitiendo mejorar la eficiencia, la trazabilidad y la confiabilidad de la gestión realizada
por la dependencia.
2 Descripción del Problema
La administración de las Aulas de Software depende actualmente de múltiples hojas de
cálculo y registros físicos que concentran la información necesaria para la operación dia-
ria. Aunque estos recursos cumplen su función, la información se encuentra distribuida
entre diferentes archivos y procesos independientes, lo que obliga al personal a realizar
constantes verificaciones manuales antes de ejecutar actividades operativas.
Procesos como la asignación de aulas para prácticas libres, el préstamo de equipos audiovi-
suales, la consulta del software instalado, la gestión de observaciones, la programación de
tareas operativas y la planificación del aseo requieren revisar simultáneamente diferentes
fuentes de información, incrementando el tiempo de respuesta y la posibilidad de errores.
Adicionalmente, actividades repetitivas como la generación de formatos institucionales,
el control de asistencia docente, la actualización de horarios y la consulta de disponibi-
lidad de las aulas continúan realizándose de forma manual, limitando la capacidad de
automatización y dificultando la obtención de información consolidada para la toma de
decisiones.
Debido a esta situación, surge la necesidad de desarrollar un sistema de información
que permita integrar los procesos operativos de la dependencia en una única plataforma,
facilitando la gestión diaria, reduciendo la dependencia de procedimientos manuales y
proporcionando información confiable para la toma de decisiones.

sitivos de red, plataformas institucionales, licencias de software, sistemas de monitoreo y
demás recursos tecnológicos.
Las credenciales estarán organizadas por categorías y cada una podrá ser consultada
únicamente por los usuarios que cuenten con los permisos correspondientes. El sistema
registrará el historial de modificaciones y consultas realizadas sobre cada credencial, per-
mitiendo mantener un control de acceso y trazabilidad de la información.
Actores:Técnico, Personal asistencial, Administrador del sistema.
Entradas:Nombre de la credencial, Categoría, Usuario, Contraseña, Descripción, Rol o
usuarios autorizados, Estado de la credencial.
Flujo Principal
1. El usuario autorizado accede al módulo de credenciales.
2. El sistema verifica los permisos asociados a su rol.
3. El usuario consulta, registra o actualiza una credencial.
4. El sistema almacena la información de forma segura.
5. Se registra automáticamente la fecha de modificación, el usuario responsable y la
operación realizada.
6. Cuando un usuario consulta una credencial, el sistema registra el acceso para efectos
de auditoría.
Reglas de Negocio
Cada credencial pertenecerá a una única categoría.
El acceso a las credenciales dependerá del rol asignado al usuario.
Las contraseñas deberán almacenarse utilizando mecanismos de cifrado seguro.
Toda consulta, creación, modificación o eliminación de una credencial deberá quedar
registrada en un historial de auditoría.
Solo los usuarios autorizados podrán visualizar las contraseñas almacenadas.

11 Arquitectura del Sistema
La arquitectura del Sistema de Gestión Operativa de las Aulas de Software se plantea
bajo una estructura modular y desacoplada, orientada a separar la interfaz de usuario, la
lógica de negocio, la persistencia de la información y los servicios de integración con otros
aplicativos.
La solución estará conformada por un frontend común desde el cual el usuario podrá
accederalosaplicativosparaloscualestengaautorización,unaAPIpropiaparalaGestión
de Aulas y una API independiente para la Gestión de Monitores.
Cada aplicativo conservará su propia lógica de negocio y su propia base de datos. La
información de autenticación, usuarios, roles y permisos será administrada de manera
centralizada por el Sistema de Gestión de Aulas.
Esta separación permitirá que cada aplicativo administre únicamente la información co-
rrespondiente a su dominio, evitando dependencias directas entre bases de datos y facili-
tando el mantenimiento y evolución futura de la solución.
11.1 Componentes principales
La solución estará compuesta por los siguientes componentes principales:
Frontend:será la interfaz utilizada por los usuarios para seleccionar el aplicativo al
cual desean ingresar, realizar el proceso de autenticación y utilizar posteriormente las
funcionalidades disponibles.
Una vez autenticado y autorizado el usuario, el frontend se comunicará directamente
con la API correspondiente al aplicativo seleccionado: Gestión de Aulas o Gestión de
Monitores.
API de Gestión de Aulas:será desarrollada utilizando NestJS con TypeScript y
será responsable de implementar la lógica de negocio relacionada con la operación de
las Aulas de Software.
Adicionalmente,seráresponsabledelaautenticacióndetodoslosusuariosdelsistemay
de la administración de usuarios, roles, permisos, dependencias y módulos habilitados.
Base de datos de Gestión de Aulas:almacenará la información operativa propia
del sistema, incluyendo usuarios, credenciales de acceso, roles, permisos, dependen-
cias, aulas, horarios, préstamos, software, equipos audiovisuales, multas, observacio-
nes, tareas, limpieza, credenciales operativas y demás información correspondiente a
los procesos definidos.
Esta base de datos será lafuente única de autenticación y autorizaciónpara los
usuarios de la solución.

frontend;
API de Gestión de Aulas;
API de Gestión de Monitores;

La integración mediante APIs permitirá incorporar en el futuro nuevos aplicativos o ser-

Para considerar una funcionalidad finalizada deberá cumplir, cuando corresponda, con los
siguientes criterios:
lógica de backend implementada;
persistencia de información implementada;
endpoint o contrato de API definido;
validaciones correspondientes implementadas;
permisos de acceso aplicados;
frontend conectado con la API real;
manejo básico de errores;
pruebas básicas realizadas;
código integrado a la rama principal de desarrollo;
revisión del código por otro integrante del equipo.
Este criterio permitirá que el porcentaje de avance represente funcionalidades realmente
utilizables y no únicamente código desarrollado.

14.6 Uso de desarrollo asistido por inteligencia artificial
El equipo podrá utilizar herramientas de desarrollo asistido por inteligencia artificial,
incluyendo Codex, para apoyar actividades como generación de código, pruebas, refacto-

La indisponibilidad temporal o los límites de utilización de estas herramientas no deberán
detener completamente el trabajo del equipo. Durante estos periodos podrán realizarse
actividades como:
revisión de código;
diseño de contratos de API;
pruebas manuales y automatizadas;
documentación;
validación de requerimientos;
revisión del modelo de datos;
preparación de tareas posteriores;
revisión e integración de cambios desarrollados por otros miembros.

14.10 Integración entre equipos
Para evitar que el desarrollo paralelo genere componentes incompatibles, los equipos de-
berán acordar previamente los contratos utilizados entre frontend y backend.
Los endpoints deberán definir como mínimo:
ruta;
método HTTP;
parámetros de entrada;
estructura de las respuestas;
códigos de respuesta;
permisos requeridos.
El frontend podrá comenzar el desarrollo de una funcionalidad utilizando datos simulados
cuando la API correspondiente aún no se encuentre disponible, siempre que el contrato
esperado haya sido definido previamente.
Posteriormente, los datos simulados deberán ser reemplazados por las solicitudes a la API
real dentro del mismo proceso de desarrollo.
14.11 Control de versiones y revisión de código
El código fuente será administrado mediante un sistema de control de versiones.
El trabajo será realizado mediante ramas de desarrollo asociadas a funcionalidades o
tareas específicas, evitando realizar modificaciones directamente sobre la rama estable del
proyecto.
Antes de integrar cambios relevantes, estos deberán ser revisados por al menos otro inte-
grante del equipo.
Las integraciones deberán realizarse con frecuencia para evitar acumulaciones de cambios
y conflictos de gran tamaño entre diferentes módulos.

14.12 Seguimiento del proyecto
El seguimiento se realizará principalmente mediante el estado de las funcionalidades in-
cluidas en cada sprint.
Se utilizarán estados similares a:
Pendiente→En desarrollo→En revisión→En pruebas→Terminado
Los bloqueos que afecten una dependencia entre equipos deberán ser reportados lo antes
posible para evitar que un frente de desarrollo permanezca detenido durante periodos
prolongados.
La planificación será revisada al finalizar cada sprint. Por lo tanto, el cronograma presen-
tado representa una guía inicial y podrá ser adaptado sin modificar el objetivo general
de disponer de una versión completa y estable en un periodo máximo aproximado de tres
meses.
